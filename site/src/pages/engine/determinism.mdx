A simulation is **deterministic** if the same starting state and the same inputs always produce the same result. It's what makes lockstep multiplayer, replays, rollback netcode, "send me the input file and I'll reproduce your bug" and golden-file tests possible.

It sounds like the default. Computers are deterministic machines, after all. But a game simulation is full of things that quietly depend on *when* and *where* it ran: the order threads finished in, the address an allocator handed out, the CPU's floating-point unit, the frame rate. Each one is a small leak, and determinism is the work of finding and plugging them.

[Game loops](/engine/game-loops/) covered the first step: a fixed timestep, so the simulation never sees the frame's delta time. This lesson covers the other leaks inside a tick. Work that spans several ticks, such as a path search on a worker thread, has its own lesson: [deadlines and async work](/engine/deadlines-and-async-work/).

## How deterministic do you need to be?

There are roughly three levels, and choosing one up front saves a lot of pain.

| Level | Guarantee | Needed for | Cost |
|---|---|---|---|
| **Bitwise, cross-platform** | Identical bits on every compiler, CPU and OS you ship | Lockstep RTS across PC/console/mobile, competitive replays shared between players | High. Strict floats or fixed point everywhere, your own maths library, constant vigilance |
| **Same build, same machine type** | Identical bits for one binary on one platform | Replays, bug repro, regression tests, lockstep on a single platform | Moderate. Fixed step, ordered iteration, owned randomness, careful threading |
| **Deterministic enough** | Close, and drift is detected and corrected | Most client/server games, rollback with an authority | Low. Checksums plus a way to resync |

Most games that think they need the first level actually need the third: a server that's authoritative, clients that predict, and **desync detection** (a hash of the important state every N ticks) so drift becomes a correction instead of a mystery. Bitwise cross-platform determinism is a genuine engineering project; pick it on purpose.

## Floating point: same maths, different answers

Floating-point addition isn't associative. `(a + b) + c` and `a + (b + c)` round at different points, and can differ in the last bits. Change the *order* of operations and the answer can change:

<EngineWidget kind="floatorder" />

Every row adds exactly the same 10,000 numbers. Only the order differs, and with values spanning many magnitudes, small ones get rounded away differently each time. The random-order button is what a parallel reduction looks like when partial sums are combined in whatever order threads finish: a different answer on most runs.

Order is the big one, but not the only one:

- **Fused multiply-add.** `a * b + c` can compile to one FMA instruction (one rounding) or a multiply then an add (two). Compilers contract to FMA by default wherever the target has it (GCC defaults to `-ffp-contract=fast` for C++, Clang to `on`, and every ARM64 chip has FMA). Pass `-ffp-contract=off` to GCC and Clang; on MSVC use `/fp:precise` without `/fp:contract` (Visual Studio 2022 or later; older versions could contract under `/fp:precise`). Whatever you choose, use the same settings for every build that has to agree.
- **`-ffast-math` / `/fp:fast`.** Explicitly allows reassociation, reciprocal approximations and ignoring NaNs. Incompatible with determinism, and often enabled in a release config by someone who wanted a few percent.
- **Transcendentals.** `sin`, `cos`, `exp`, `pow` and `atan2` come from the platform's maths library and are *not* required to be correctly rounded. MSVC, glibc and Apple's libm can disagree in the last bit. Ship your own implementations for anything inside the simulation.
- **x87 and extended precision.** Old 32-bit x86 code could keep intermediates in 80-bit registers and round only when spilling to memory, so results depended on register allocation. SSE2 (the default on x64) fixed this, but it's why old advice about float determinism is so gloomy.
- **SIMD.** A vectorised sum adds in lanes and combines them at the end, a different order from the scalar loop. Compilers only do this to float reductions when reassociation is allowed (fast-math, `/fp:fast`, a vectorise pragma, `omp simd reduction`, or a compiler that defaults to fast floating point, as Intel's does). Hand-written SIMD and libraries that pick an SSE, AVX or NEON path at runtime do it routinely, so the same binary can give different answers on different CPUs.
- **Denormals.** Flush-to-zero and denormals-are-zero modes are per-thread CPU flags. A library or driver that sets them on one thread changes results only there.

What does work: IEEE 754 guarantees that `+ - * /` and `sqrt` are correctly rounded. With SSE2, no FMA contraction, no fast-math, your own transcendentals and a fixed order of operations, floats are bit-reproducible across x64 compilers and largely across ARM. It needs discipline, and a test that catches the day someone breaks it.

### Fixed point

The alternative is to not use floats in the simulation at all. A fixed-point number is an integer with an implied scale (16.16 means "divide by 65,536"), and integer arithmetic is identical everywhere. The trade is real, though:

- **Range versus precision.** 16.16 gives ±32,768 with a resolution of 1/65,536. A large map with fine physics doesn't fit, so you end up with several formats and conversions between them.
- **Overflow.** Multiplying two 16.16 values needs a 64-bit intermediate. Forget once and positions wrap silently.
- **Everything is yours.** Square roots, trig, normalisation, every library you might have used. Physics engines, pathfinding and animation libraries all assume floats.
- **It's slower** for anything beyond add and multiply, and it doesn't vectorise as neatly.

So lockstep games that use fixed point often limit it to the state that must match (positions, health, timers) and keep floats for presentation. The common compromise is "deterministic enough": strict floats, desync detection, and a correction when two platforms drift.

## Random numbers

A random number generator is a deterministic sequence: seed it the same and it yields the same numbers. The problem is *who draws which number*. If two systems share one generator, any change in the order they run (a new system, a skipped one, a different thread schedule) shifts every number after it.

Run the same tick several times with each strategy:

<EngineWidget kind="rngstreams" />

- **One shared generator** gives a different outcome whenever the processing order changes. Even single-threaded, adding an effect that draws one extra number reshuffles every loot roll after it.
- **A generator per thread** looks like a fix and isn't. Which thread runs which unit depends on scheduling, so the same unit draws from a different stream each run.
- **A counter-based random number** has no state at all. It's a hash of everything that identifies the question: `hash(world_seed, entity_id, tick, purpose)`. Ask the same question and you always get the same answer, regardless of order or thread.

```cpp
// A stateless, order-independent random number for the simulation.
// Any good 64-bit mixer works: SplitMix64, PCG's output function, Philox (used by GPUs).
inline uint64_t mix(uint64_t x) {
    x ^= x >> 30; x *= 0xbf58476d1ce4e5b9ull;
    x ^= x >> 27; x *= 0x94d049bb133111ebull;
    return x ^ (x >> 31);
}
inline uint64_t sim_rand(uint64_t seed, uint64_t entity, uint64_t tick, uint64_t purpose) {
    return mix(seed ^ mix(entity ^ mix(tick ^ mix(purpose))));
}
// Uniform [0, n) without implementation-defined distributions:
inline uint32_t sim_range(uint64_t r, uint32_t n) { return (uint32_t)(((r >> 32) * n) >> 32); }

uint32_t loot = sim_range(sim_rand(world.seed, e.id, tick, Purpose::Loot), 100);
```

So "per thread or per process?" is the wrong axis. Streams should be **per question**: keyed by what is being decided, not by who is running the code. Where a stateful generator is more convenient (a system that draws many numbers in sequence), give it its own generator seeded from `sim_rand(seed, system_id, tick, 0)` at the start of the tick and only use it from that system, in a fixed order.

<Tip kind="warn" title="The standard library will betray you">
`std::mt19937` itself is fully specified, but `std::uniform_int_distribution`, `std::uniform_real_distribution` and `std::normal_distribution` are not: libstdc++, libc++ and MSVC produce different numbers from the same engine. Do the range reduction yourself. `rand()` differs between platforms entirely.
</Tip>

## The usual suspects

Beyond floats and randomness, these are the bugs that actually turn up in desync reports:

- **Iteration order of hash containers.** `std::unordered_map` order depends on bucket count, insertion history and the standard library. Iterating one to apply effects is a classic desync. Iterate something ordered, or collect and sort first.
- **Pointer values.** Sorting by pointer, hashing pointers, or using an address as a tie-breaker changes with every allocation pattern and with ASLR. Use ids.
- **Unstable sorts.** `std::sort` doesn't preserve the order of equal elements, and different implementations order them differently. Use `std::stable_sort` or add a tie-breaker (entity id) so there are no equal elements.
- **Reading the clock.** Anything in the simulation that calls `clock()`, `now()` or uses the frame's delta time. Simulated time is `tick × dt`.
- **Uninitialised memory and padding.** Reading an uninitialised field is undefined; hashing or comparing a struct with `memcmp` includes its padding bytes, which contain whatever was there before.
- **Input timing.** Input must be stamped with the tick it applies to and applied at that tick, not "whenever it arrived".
- **Floating-point state shared with other code.** A plugin, driver or audio thread that changes rounding or denormal modes.
- **Presentation leaking into the sim.** Gameplay that reads an animation's current frame, a particle's position or whether something is on screen.
- **Undefined behaviour.** Signed overflow, out-of-bounds reads, data races. Optimisers are allowed to do different things with it in different builds.

<Tip title="Catch drift the moment it happens">
Hash the simulation state every tick (or every N ticks) in debug builds and log it. Record a session, replay it, and compare the hashes: the first tick where they differ points at the system to look at. Run the same replay on every platform in CI and you'll find the FMA flag someone added before your players do. Hash *components*, not structs with padding, and hash in a defined order.
</Tip>

## Threads

Threads are where determinism usually goes to die, because the order threads finish in is up to the operating system. The fix isn't to avoid threads; it's to make sure **the order things finish in can't affect the result**. Three rules cover most of it.

**1. Partition, don't share.** Split work so each job owns a disjoint slice of the output: job *k* updates entities `[k×n/K, (k+1)×n/K)`. Jobs read shared state from the previous tick but never write it. This is what an ECS scheduler does when it runs systems with non-overlapping writes in parallel.

**2. Buffer side effects, merge in a fixed order.** When jobs need to affect things outside their slice (spawn a projectile, deal damage to another unit, emit an event), they append to a **per-job output buffer**. After all jobs finish, the main thread merges the buffers in *job index* order, or sorts the combined commands by a stable key such as `(target_id, source_id, sequence)`. Completion order never appears in the result.

```cpp
struct DamageCmd { EntityId target, source; int32_t amount; };

std::vector<std::vector<DamageCmd>> out(job_count);   // one buffer per job, not per thread
parallel_for(job_count, [&](int job) {
    for (EntityId e : slice(job)) attack(e, out[job]);  // append only to this job's buffer
});
for (auto& buf : out)                                  // merge by job index: deterministic
    for (auto& cmd : buf) apply(cmd);
```

Buffers are per *job*, not per *thread*: a thread pool may run job 3 on any thread, but job 3 always writes `out[3]`. flecs' command queues work the same way: commands queued from multi-threaded systems are merged at the sync point in a fixed order.

**3. Reduce in a fixed shape.** For sums, minimums and counters, each job writes its partial result to its own slot, and the slots are combined in index order (the "4 threads, then combine" row in the float widget is deterministic for exactly this reason). Atomic `fetch_add` on an integer is fine, since integer addition is associative. Atomic float accumulation is not.

The same rule stretches across ticks. Work handed to a worker and collected later must enter the simulation on a tick that doesn't depend on how fast the worker went: [deadlines and async work](/engine/deadlines-and-async-work/) shows how.

## Takeaways

- **Decide what level you need.** Same-build determinism plus desync detection covers most games; bitwise cross-platform determinism is a deliberate project.
- **Floats are deterministic only in a fixed order** with fixed compiler settings and your own maths functions. Fixed point trades that discipline for a different one.
- **Key random numbers by the question, not the thread.** `hash(seed, entity, tick, purpose)` can't be reordered.
- **Threads may run in any order; results must not depend on it.** Partition writes, buffer side effects per job, merge by index.
- **Ban the usual suspects** from the simulation: hash-map iteration order, pointer values, unstable sorts, the clock, padding bytes.
- **Hash the state every tick in testing**, so the first divergent tick tells you where to look.

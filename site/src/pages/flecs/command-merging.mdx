[The commands lesson](/flecs/commands/) showed that operations inside a system are queued, and that commands for the same entity are **batched**: the first command for an entity applies all of them at once, so it moves once, to its final table. That's great for performance. It also means observers only hear about what survives the batch.

That raises some questions. What happens when the queue says *remove, then add* the same component? Does an `OnRemove` observer see the value you `set` between two removes? The debugger below answers them. Each line runs a system once on its own entity (A to D, each starting with `Foo{40}`), and three observers record what they see.

<FlecsDebugger scenario="batching" />

## What observers see

Observer calls are shown with the value of `Foo` they were given.

| Case (queued in one system) | Observers see | Moves |
|---|---|---|
| **A** `remove<Foo>()`, `add<Foo>()` | `OnRemove(40)`, then `OnAdd(0)`. A really leaves and re-enters the table, so Foo is constructed fresh: **0**, not the old 40. | 2 |
| **B** `remove`, `set<Foo>({50})`, `remove` | `OnRemove(40)` **once**. The 50 only ever existed in the queue, so nobody sees it. | 1 |
| **C** `remove`, `set<Foo>({50})` | `OnRemove(40)`, `OnAdd(0)`, `OnSet(50)`: a full remove, then a fresh add and set. | 2 |
| **D** `set<Foo>({50})`, `remove` | `OnRemove(50)`, and no `OnSet`. D already had `Foo`, so the `set` wrote 50 straight into the column when it was called; only its `OnSet` was queued, and the batch drops it because `Foo` is gone by the end. | 1 |

The rule behind all four: **the command queue applies your operations in order. Batching doesn't invent events, but it drops the ones for an add or set that a later remove in the same batch cancels out.** A queued remove really removes, so the component's `OnRemove` sees the value that was in storage, and a later add constructs a new value. B's add and set of 50, and D's `OnSet`, never reach an observer: an `OnSet` observer that mirrors values into another system won't hear about them.

<Tip kind="warn" title="A queued remove and add is not a reset to the old value">
If an observer has to see a "reset" (remove then add), you get a freshly constructed value, not the old one, and every observer of both events runs. If you just want to reset a component, `set` it to its initial value. If you need "it was removed" and "it was added" handled separately, make them two separate sync points, for example two systems with a merge between them.
</Tip>

<Tip kind="note" title="Why the moves column matters">
Watch the stats line and the move events. A and C move twice each (out of the table and back in), which is the honest cost of what the code asked for. If you queue remove/add pairs every frame for a reset, that's two moves per entity per frame: another reason to use `set`.
</Tip>
